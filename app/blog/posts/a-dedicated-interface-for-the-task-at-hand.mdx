My current system for working with agents, mostly coding but also general research, is to build my own interface for it. I think you have to create a dedicated interface for the task at hand. I have done this a few times now. The most recent one is [Plan Viewer](/projects/planboard) (now Planboard), which is my daily coding UI.

The goal was to bring as much of the software development lifecycle as possible into one place. That does not mean replacing the tools that already hold the information. Issues lived in Linear, and later in Jira. Code lives on GitHub. Some of the conversation happens in Slack. Plan Viewer integrates those places instead of copying them.

On top of that, I wanted my own notes, working files, and some sense of work breakdown and tracking. And I wanted that stuff to be private to me. A lot of the files that help me break down work are scratch material. They should not litter the issue tracker or the PR.

Plan Viewer is a web app, but it runs off a local server, so it is local to my machine. You could run it on a server. I have gone back and forth on doing that.

## Every reference opens in place

The part that matters most is removing every bit of friction around related information. Here is a daily plan. It is Markdown on disk, and the viewer renders it as cards:

![A daily plan in Plan Viewer: scheduled tasks, then two milestones with links to two PRs, a commit, a Jira issue and a Slack message](/images/posts/a-dedicated-interface-for-the-task-at-hand/today.png)

The viewer aggressively detects known objects in the text. PR numbers, commit hashes, Jira keys, and Slack links all become links with an icon. Click one, and it opens in a modal. You never navigate away from the page.

A PR opens in my own view of it, not GitHub's. The description, the files, the commits, and the diff are all there. The left column also shows what links to the PR, so this one points back to the daily plan that mentions it.

![PR 29 from the Plan Viewer repository open in a modal, with status, author, linked daily plan and commits on the left, the changed files in the middle, and the rendered description on the right](/images/posts/a-dedicated-interface-for-the-task-at-hand/pr.png)

A commit hash opens the commit with its diff:

![A commit from the Plan Viewer repository open in a modal, with its five changed files on the left and a split diff of the guide on the right](/images/posts/a-dedicated-interface-for-the-task-at-hand/commit.png)

A Jira key opens the ticket, with its status, parent, children and latest status update:

![A Jira epic open in a modal, with its fields on the left and its status update, description and child issues on the right](/images/posts/a-dedicated-interface-for-the-task-at-hand/issue.png)

A Slack link opens the thread in a modal too. The demo workspace in these screenshots has no Slack token, so there is no Slack shot here.

The key thing is that everything is tightly interlinked. I can go look at the primary source quickly, but I never leave the context I am in. When the plan says "review the PR and check that commit", the PR and the commit are one click away, and closing the modal puts me back on the same line of the plan.

## The system improves itself

Once a system like this exists, you can use its own machinery to change how it works.

One morning I was having a hard time keeping track of all the chat threads running on my machine. I was telling Claude to invoke Codex itself, so Claude was driving Codex. But those Codex threads were just running. They did not show up in any UI.

So I had it update Plan Viewer to list all of the active threads, with a click that opens each one in its desktop app. A nuisance became a feature. That page has since grown into [Plan Viewer's Chat Threads page](/blog/plan-viewer-chat-threads), with subagents nested under their parents and a status for threads that wait on a background task.

That is the pattern now. If I am clicking around for something or struggling to find it, I ask the agent to put it on this surface. Each fix makes the interface a little more specific to how I actually work, which is the point of having a dedicated one.

## When to build one

There is a decision under all of this. When a new kind of work shows up, do I make it fit the tool I already have, or do I go build a dedicated interface for it?

Nearly always I start with whatever I've got. A chat thread, a Markdown file, the GitHub page. I only build something when I notice I keep fighting that tool for the same thing, and then I specialize it. The thread list above went that way: the threads were running fine without a page, until keeping track of them got in my way.
