Diagram Studio started as a diagram editor that runs entirely in the browser. You draw a diagram and improve its layout in small passes, and the diagram is saved in browser storage. That works when I'm the only one drawing. It doesn't work once I want an agent to draw the first version and me to fix it up, because the agent can't reach into my browser's storage.

What I wanted was one local file that both of us edit. An agent writes the diagram. I open it and get a good automatic layout. I drag a few things where they belong and close the viewer. The agent adds a node later, and my arrangement mostly holds. No export-and-import step anywhere in that loop.

That became [Draftably](https://github.com/byronwall/draftably), on npm as `draftably`.

## The file

A `.draft` file is plain text, one statement per line:

```text
diagram "Checkout architecture" version=1

group platform "Commerce platform" color=mint
node api "API gateway" in=platform
group services "Domain services" in=platform
node orders "Orders" in=services
node payments "Payments" in=services shape=pill
node db "Postgres" color=violet

edge dispatch api -> orders "create order"
edge persist orders -> db "persist" kind=async

layout root flow gap=48
near payments orders side=right gap=32
pin db x=900 y=40
```

The file holds the model and the layout recipe, plus a few refinements. It never holds a picture of the finished layout. The same file always compiles to the same geometry, and `draftably inspect --json` is byte-identical across runs. That makes it something an agent can check with `draftably check` and `inspect --svg`, without opening a browser.

The refinements are where most of the design went. A drag shouldn't become a permanent absolute coordinate, because then the next change can't move anything. So there are different strengths. `near` and `stay` are soft, and they give way to keep siblings from overlapping. `pin` is hard. Positions are relative to the parent group, so moving a group moves everything inside it.

## The loop

`draftably open file.draft` serves the editor and watches the file. When the agent edits the file, the drawing updates. When I edit in the viewer, the change saves to the file. If the agent writes a broken line, the viewer keeps the last valid drawing and shows the error line.

Two writers on one file need a rule so neither silently erases the other. Each save carries the revision it started from. A stale save gets a 409, and invalid source gets a 422. Writes are atomic, and the watcher looks at the folder, so editors that save by renaming still get noticed.

## Layout engines in the file

The editor already had several layout engines. The question was whether their results could be saved as source. An engine has to give the same answer from the file alone, without depending on where the boxes happened to start. I checked every engine on three samples. Moving the starting positions never changed the result, except for one engine, which was left out. The rest can be named per scope:

```text
layout root engine=compound-flow
layout services engine=grid
routing edge-gap=24 corner-radius=0
```

The interactive tools were harder. Improve, timeline steps and the layout brush all start from whatever is currently drawn, so no recipe can reproduce their results. Those get saved as soft `stay` positions for just the objects that moved. A second brush stroke updates a few numbers in place instead of rewriting the block. A test runs Apply, Improve, timeline Keep, a brush stroke, an outside addition and a server restart in a row. After every step, the viewer's geometry has to match `draftably inspect` of the saved file.

## Themes the CLI can draw too

Themes came next: five presets, 14 color families with numeric shades from 50 to 950, and custom families defined in the file. The first palettes had poor contrast. The fix generates shades in two bands that skip the muddy mid-tones: pale fills with dark text at 7:1 or better, and strong fills with white text at 4.5:1 or better. Tests check every theme, family and shade.

*Graphite, Signal, Mulberry and Midnight, all from the same source.*

Text was the subtle part. If the browser measures text one way and the CLI another, titles wrap differently and the geometry stops matching. So the three fonts are bundled, and their character widths are stored in the repo. The compiler, the canvas and the CLI all wrap titles the same way, without measuring anything in the DOM.

## Teaching the agent the format

The last piece is a skill. `draftably skill install` drops a `SKILL.md` into `.claude/skills`, covering the write → check → inspect → open workflow and the full syntax. A test compiles every example in the skill and fails if the skill leaves out a statement or engine that the parser accepts. A CI step fails any PR that changes the syntax without also updating the skill. Otherwise the skill would drift from the parser, and agents would write diagrams the parser rejects.

`draftably open` on a folder now opens a start page with that folder's diagrams, newest first. Files an agent writes show up within a few seconds, without a reload.

## Where it stands

The authoring loop works: agent writes, I refine, and the file holds both. Architecture diagrams and user flows were the first targets. Dependency trees and call stacks matter too but haven't been pushed as hard. Views, presentation modes and checkpoints are left out on purpose. The file format leaves room for them, but none of them were needed for the loop.

```sh
pnpm dlx draftably open
```
